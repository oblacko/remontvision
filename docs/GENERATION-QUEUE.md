# Генерация: очередь и ёмкость — суть проблемы

Дата: 2026-11-12. Статус: частично реализовано. Сделано: lease + `claimed_by`, `FOR UPDATE SKIP LOCKED`, семафор image-вызовов, `WORKER_CONCURRENCY` (default 100), восстановление зависших рендеров, асинхронная очистка комнаты. Ещё не сделано: per-user справедливость и капы, отдельный сервис воркера, SSE, нагрузочные/chaos-тесты — см. `docs/redesign/2026-11-11-redesign-codebase/plan.md` и `docs/HISTORY.md`.

## Контекст

- Мульти-стиль генерация: пользователь выбирает до 10 пар «стиль × концепт», каждая пара — отдельный рендер (`renders.style` / `renders.concept`, миграция `050`).
- Все варианты создаются сразу и ставятся в очередь `renders` со статусом `queued`.
- Воркер живёт внутри процесса API (`src/jobs.js`, `startWorker`), забирает задачи (`claimNextRender`) раз в 2 секунды и держит до `WORKER_CONCURRENCY` рендеров одновременно (default 100, `src/workerknobs.js`).
- Image-вызовы идут параллельно в пределах семафора (`withImageSlot` в `src/openrouter.js`): лимиты система/провайдер/пользователь, пауза `image_min_gap_ms` по умолчанию 0 (`src/renderconfig.js`, админка «Генерация»).
- Очистка комнаты — отдельная асинхронная задача на первом enqueue: `rooms.cleanup_status`, до 3 попыток, shell переиспользуется; рендер ждёт shell ≤3 мин.

## Суть проблемы

> Часть ниже — исходный анализ 2026-11-11. На 2026-11-12 image-вызовы идут параллельно в пределах семафора, `WORKER_CONCURRENCY` по умолчанию 100, пауза 0; пункты про один слот, 2 рендера и 10-секундную паузу устарели. Актуальны fairness/caps, отдельный worker, SSE и 24-часовой sweeper.

1. **Фича умножает число задач, но не добавляет пропускной способности.** До 8 рендеров на пользователя при том же одном image-слоте.
2. **Пропускная способность.** Один рендер ≈ латентность генерации (15–30 с) + пауза 10 с → примерно **90–150 рендеров в час**. 1000 пользователей × 8 = **8000 рендеров → 55–90 часов** непрерывной работы, чтобы очередь опустела (2–4 суток).
3. **Нет справедливости.** Очередь глобальная FIFO (`ORDER BY created_at`), без лимита на пользователя и без round-robin. Один активный пользователь занимает очередь; пришедшие позже ждут дни. Нет ограничения «сколько задач один пользователь может держать в очереди».
4. **24-часовой уборщик.** `staleRenders(24 * 60)` помечает рендеры старше 24 часов ошибкой «Генерация не завершилась за 24 часа» и возвращает кредит. При бэклоге больше суток это массовые ошибки у пользователей, хотя генерация просто не дошла до задачи.
5. **Поллинг клиента — отдельная точка отказа.** `pollRoom` в `GenerationPanel.tsx` опрашивает `/api/rooms/:id` каждые 2 секунды на каждого активного генератора. 1000 генераторов ≈ **500 запросов/с** в единственный Node-процесс и Postgres — сайт деградирует раньше, чем очередь начнёт двигаться.
6. **Сериализация завязана на процесс.** `imageChain` — модульная переменная в памяти. Вторая реплика приложения получит собственный слот и начнёт параллельно долбить провайдера (429); простое горизонтальное масштабирование контейнера ломает инвариант.
7. **429 от провайдера.** При таком объёме почти гарантированы; ретраи 10/20/40 с ещё сильнее снижают throughput.

## Что не было учтено в дизайне фичи

- расчёт ёмкости (сколько рендеров в час выдерживает система);
- лимит одновременных задач на пользователя и лимит очереди на пользователя;
- честность распределения между пользователями;
- прогресс «готово N из 8» вместо абстрактного «в очереди»;
- поведение при перегрузке (честный отказ вместо молчаливого ожидания);
- нагрузка от поллинга при массовых одновременных генерациях;
- влияние 24-часового таймаута на длинный бэклог.

## Направления решения (не реализовано)

- вынести воркеры из API-процесса, масштабировать их отдельно;
- очередь с `FOR UPDATE SKIP LOCKED` (Postgres) или Redis/BullMQ; несколько воркеров забирают задачи атомарно;
- per-user лимит 1–2 одновременных рендера + round-robin между пользователями;
- cap очереди на пользователя и глобальный backpressure;
- глобальный token bucket на image-вызовы с адаптивной паузой (растёт при 429, снижается при стабильности);
- SSE/WebSocket или редкий поллинг вместо 2 с;
- прогресс по каждому варианту и общий «N из 8»;
- честный ответ 429/503 «сервис перегружен, попробуйте позже»;
- пересчитать таймауты под нагрузку, не убивать задачи старше 24 ч в длинном бэклоге.

## Код-референсы

- `src/jobs.js` — `startWorker` (тик 2 с, `running >= 2`), `claimNextRender`, `staleRenders(24 * 60)`.
- `src/openrouter.js` — `withImageSlot`, `IMAGE_MIN_GAP`, ретраи на 429.
- `src/renderconfig.js` — `image_min_gap_ms` (по умолчанию 0, админка).
- `web/src/components/GenerationPanel.tsx` — `pollRoom` (2 с).
- `migrations/050_renders_style_concept.sql` — стиль и концепт на рендере.
