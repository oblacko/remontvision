# «Воплотить дизайн»: пилот и будущий поиск товаров

Дата: 2026-10-29. Статус: **Phase 2 реализована (список товаров); смета — следующий этап**.

## Текущая реализация

- Продукт: `рендер → detail vision → список товаров`. Количества, площади и итоговая сумма не считаются.
- Один запуск «Найти товары» стоит 1 кредит; повторное открытие готового списка бесплатно; при ошибке или нуле проверенных товаров кредит возвращается.
- Магазины: Yandex Search API + allowlist (`divan.ru`, `stoolgroup.ru`, `divanboss.ru` и др.). Яндекс Маркет отдаёт серверу SmartCaptcha и исключён.
- Слои: hero (5–8 предметов, визуальная оценка), отделка (text), техника/сантехника (text), текстиль (text), комплектующие (rules).
- API: `POST /api/renders/:id/procurement`, `GET /api/procurement/:id`, `GET /buy/:candidateId`.
- Следующий этап: площади, количества, упаковки, итог, PDF — отдельный домен `estimate`, который ссылается на procurement.

## Продуктовая цель

После завершения работы над дизайном пользователь выбирает конкретный рендер и запускает «Воплотить дизайн». Система разбирает видимые предметы и помогает найти, где их купить.

Текущая предварительная смета остаётся: она подбирается до/после генерации из curated-каталога. Новый режим связан с выбранным `render_id` и отвечает на другой вопрос: «Что купить именно для этого результата?»

Главное решение для пилота: **сохранить многошаговый качественный поиск, но ограничить количество предметов, магазинов и расходы на каждый запуск**. Реферальная программа не нужна. Поисковый провайдер выбирается по результатам замера цены и качества, а не заменяется бесплатными ссылками.

## Что уже можно переиспользовать

- `src/openrouter.js` — `parseRender()` уже извлекает `items`, `surfaces`, `visible`, `electrical`; `matchCatalog()` сопоставляет items с локальным каталогом.
- `src/jobs.js` — Vision уже вызывается после генерации. Сохранить `parsed.items` в `renders.analysis` для предварительного фильтра; подробный разбор выбранных hero-предметов выполняется отдельно один раз на procurement run.
- `src/productimport.js` — импорт известной карточки по URL: JSON-LD/OpenGraph, фото, цена, бренд, артикул, габариты, доступность, allowlist и SSRF-защита.
- `products`, `render_items`, `/go/:id` — реальные карточки каталога, статусы `curated|matched|verified`, журнал переходов.
- `app_settings` и админка — механизм настроек без деплоя.

Текущий каталог демонстрационный: реальные карточки сначала нужно импортировать. Порог `matchCatalog()` — текстовый матчинг, а не визуальные «80% совпадения».

## Качественный пилот: сокращаем охват, а не глубину поиска

### Неприкосновенное ядро исходного пайплайна

1. Для каждого предмета создаётся подробная атрибутная карточка, а не одна строка keywords.
2. Поиск идёт **в несколько проходов**: результат оценивается, следующий запрос учитывает причину неудачи предыдущего.
3. Модель участвует в формулировании запросов и визуальной оценке, но не выдумывает товары, URL, цены и артикулы.
4. Кандидат превращается в карточку только после открытия реальной страницы и извлечения данных.
5. Визуальное сходство оценивается отдельно; 80+ является обязательным порогом для основного варианта, 70–79 — только альтернативой.
6. Если хороший вариант не найден, предмет честно остаётся unresolved. Поисковая ссылка — fallback, а не замена качественному результату.
7. Реферальная программа отключена и не влияет на ранжирование.

Однопроходный сценарий «один промт → список товаров» не соответствует этому плану.

### Область пилота

- Одна комната и allowlist магазинов; Яндекс Маркет исключён из серверного пайплайна из-за SmartCaptcha.
- 5–8 hero-предметов с визуальной оценкой; полный комплект комнаты собирается по room template.
- Отделка, инженерия, текстиль и комплектующие входят в список сразу: отделка/техника ищутся текстом, комплектующие добавляются по правилам.
- До 5 проверенных кандидатов на раунд, до 2 раундов на предмет в текущей реализации.
- Reverse image search включается только для unresolved предметов и может быть выключен администратором.
- Один основной результат и до двух достойных альтернатив. Не требовать два магазина любой ценой.

Так сокращается стоимость запуска, но каждый выбранный предмет проходит качественный цикл.

### Обязательный многошаговый цикл на предмет

```text
attribute card
  → round 1: exact query
  → fetch real candidates
  → verify product pages
  → visual scoring
  → 80+: accept
  → иначе round 2: refined form/material/color query
  → verify + score again
  → 80+: accept
  → иначе round 3: reverse image search по crop, если включён
  → verify + score again
  → 80+: accept
  → 70–79: alternative
  → иначе unresolved
```

Это последовательный управляемый цикл, а не три одинаковых запроса параллельно. После первого раунда модель получает причины отказа — другая форма ножек, неправильный материал, другой тип радиатора — и меняет следующий запрос с их учётом. При достижении 80+ дальнейшие раунды не оплачиваются.

Состояния item: `extracted → searching → evaluating → refining → verified|alternative|unresolved`. Все раунды и причины переходов сохраняются, чтобы повторный запуск продолжал работу с нужного места.

### Разбор изображения

Существующий `parseRender()` используется как предварительный фильтр, но его кратких description/keywords недостаточно. Для выбранных 5–8 hero-предметов выполняется один подробный разбор на run:

- категория и подтип;
- цвет, материал, форма, фактура и отличительные детали;
- оценка размера и достоверность этой оценки;
- 3–5 синонимов и поисковых формулировок;
- bbox и crop для визуального сравнения;
- `SEEN|HIDDEN`, confidence и количество.

Разбор делается один раз и кэшируется. Он не повторяется в каждом поисковом раунде.

### Проверка и оценка кандидатов

1. Discovery provider возвращает URL и поисковые метаданные.
2. Код канонизирует URL, удаляет дубли и отсекает неподходящие страницы.
3. `productimport`/adapter открывает карточку и получает реальные фото, цену, наличие, характеристики, SKU/MPN и `checked_at`.
4. Vision scorer сравнивает crop с фото кандидата и возвращает компоненты цвета, материала, формы и размера, объяснение и неопределённости.
5. Код применяет hard gates и пороги, сохраняет решение и выбирает следующий раунд.

`80+` означает высокое визуальное сходство, не идентичность. Точное совпадение требует brand/model/MPN или ручного подтверждения. Пороги калибруются на человеческой разметке, а не принимаются на веру из самооценки модели.

### Как снижать расходы без потери логики поиска

- Меньше предметов на run, а не один поверхностный проход на весь интерьер.
- Ранний выход после первого результата 80+.
- Проверять страницы только у перспективных кандидатов, а не у всей выдачи.
- Кэшировать подробный разбор, поисковые ответы, карточки и визуальные сравнения.
- Использовать общий кэш кандидатов для повторных запросов разных пользователей с учётом магазина и региона.
- Reverse search только после неудачи текстовых раундов.
- Ограничить concurrency и установить денежный лимит на run/item.
- Позволить администратору запускать дорогой добор вручную только для unresolved предметов.
- Реферальные ссылки не создавать: это не снижает качество поиска.

Перед реализацией провести spike на 20–30 размеченных предметах и сравнить доступные discovery-подходы: Yandex Search API, модель с официальным web-search tool и официальные фиды магазинов. Сравнивать стоимость полного принятого результата, а не цену одного запроса. Выбранный провайдер должен отдавать реальные источники, которые можно открыть и проверить. Скрытый scraping поисковой выдачи не считается стабильной заменой API.

## Минимальная архитектура итеративного поиска

### Отдельный контур, не смешанный с curated-каталогом

- `procurement_runs`: `id`, `render_id`, `user_id`, `status`, `config`, `region`, `cost`, `created_at`, `finished_at`.
- `procurement_items`: `run_id`, `layer`, `category`, `subtype`, `attributes`, `keywords`, `bbox`, `crop_path`, `quantity`, `visibility`, `confidence`, `status`, `sort`.
- `procurement_search_rounds`: `item_id`, `round_no`, `kind`, `provider`, `query`, `rejection_reasons`, `results_count`, `best_score`, `decision`, `cost`, `created_at`.
- `procurement_candidates`: `item_id`, `round_id`, `provider`, `product_id?`, `store`, `canonical_url`, `title`, `image_url`, `price`, `currency`, `availability`, `sku`, `checked_at`, `link_status`, `match_score`, `score_breakdown`, `match_reasons`, `selected`, `raw_payload`.

`search_rounds` обязателен уже в пилоте: без него многошаговый поиск нельзя возобновлять, кэшировать и аудировать. Цена, фото и артикул появляются только после проверки карточки. Снимок кандидата сохраняется, чтобы изменение внешнего магазина не переписывало старую закупку незаметно.

### Orchestrator и providers

Orchestrator владеет циклом, порогами, лимитами и переходами. Search provider только ищет, importer/adapter проверяет страницу, scorer сравнивает изображения:

```text
orchestrator
  → search provider
  → canonicalize/dedupe
  → product importer
  → visual scorer
  → accept | next round | unresolved
```

Провайдеры можно заменять после benchmark без изменения state machine и UI. Не добавлять пустые интеграции и переключатели в админку до реальной реализации провайдера.

### Минимальные настройки админки

Один ключ `app_settings.procurement.settings.v1`:

- `enabled` — вся функция, по умолчанию `false`;
- `max_items` — по умолчанию 5;
- `max_rounds` — по умолчанию 3;
- `min_score` — по умолчанию 80;
- `max_candidates_per_round` — по умолчанию 5;
- `text_search_provider` — только реализованный и проверенный вариант;
- `reverse_search_enabled` — по умолчанию `false`;
- `max_run_cost` — обязательный предохранитель;
- `search_links_enabled` — fallback для unresolved;
- `default_store` — сначала `market`.

Позже отдельно добавляются магазины, партнёры, автоматическое обновление цен и лимиты по каждому провайдеру. Секреты API остаются в env. UI не должен показывать переключатель неработающей интеграции.

### Партнёры независимы от поиска

Всегда хранить `canonical_url`. Партнёрская ссылка создаётся на outbound-этапе только если для магазина включён работающий партнёр. При ошибке партнёрского API можно перейти по canonical URL, не теряя найденный товар.

Для каждого перехода сохранять run/item/candidate и дополнительный идентификатор партнёра. Партнёр никогда не повышает match score и не получает приоритет в выдаче.

### API пилота

```text
POST  /api/renders/:id/procurement
GET   /api/procurement/:runId
POST  /api/procurement/:runId/items/:itemId/research
PATCH /api/procurement/:runId/items/:itemId/selection
GET   /buy/:candidateId
```

Внешний многошаговый поиск выполняется фоновым worker с idempotency, лимитами и возобновлением по item/round. Повторный запуск не должен заново оплачивать успешные предметы. Пользователь видит прогресс и может открыть частичный результат до завершения всего run.

## Полный будущий пайплайн

### 1. Конфигурация выбранного рендера

Freeze `render_id`; регион, бюджет/класс, площадь и размеры помещения. Цена и наличие зависят от региона. Метраж нельзя надёжно восстановить по одному рендеру.

### 2. Подробный Vision-разбор

Слои отделки, инженерии, мебели, текстиля и декора. Для каждого предмета: subtype, bbox, crop, цвет, материал, форма, фактура, размер и его достоверность, количество, поисковые синонимы, `SEEN|HIDDEN|NOT_SEEN`, confidence. Личные вещи и скрытая проводка исключаются.

Перед дорогим поиском пользователь может удалить или исправить предмет.

### 3. Комплектность

Детерминированные правила: кровать → матрас; светильник → лампы; шторы → трек/крепления; ламинат → подложка/плинтус/порожки и запас 10–15%; обои → клей и запас; LED → блок питания/профиль. Это рекомендации по комплектности, а не аналоги с фото.

### 4. Три волны discovery

1. Точный текстовый запрос.
2. Запрос по силуэту и цвету.
3. Reverse image search по crop для важных или нерешённых предметов.

Ограничить 5–10 кандидатами, concurrency и бюджетом на run. Кэшировать запросы и повторно использовать результаты. Канонизировать URL, удалять дубли, отсекать неправильную категорию и б/у.

### 5. Проверка карточек

Из известного URL через importer/adapter получать название, фото, цену, наличие, характеристики и SKU/MPN. Модель не генерирует URL, цену, наличие и артикул. Фиксировать `checked_at` и регион.

### 6. Визуальное сравнение

Отдельный scorer сравнивает crop и фото кандидата. Сначала category-specific hard gates, затем компоненты цвета, материала, формы и размера с объяснением. Неизвестный атрибут ограничивает достоверность, а не silently получает полный балл.

`80+` означает «высокое визуальное сходство», не «точное совпадение». Идентичность требует совпадающего brand/model/MPN или ручного подтверждения. Пороги калибруются на human-labeled данных.

Отдельно хранятся `match_score`, `link_status`, `checked_at`, `region`, `availability`. Поисковая ссылка не называется вечной; статус прямой ссылки действует на момент проверки.

### 7. Выбор и закупка

Пользователь выбирает основной вариант. Альтернативы не складываются в бюджет. Если второго хорошего магазина нет, показывается один вариант или «не найдено». Работы отдельно от товаров.

UI: группы, фото, цена, магазин, количество, объяснение сходства, время проверки, альтернативы, переподбор; позже hotspots и PDF/CSV.

## Яндекс Маркет (исключён из пилота)

Серверные страницы Маркета отдают SmartCaptcha, поэтому магазин не используется как основной источник карточек. Раздел сохранён для будущего исследования официальных API/фидов.

Referral API — монетизация известной страницы, а не discovery. Текстовый `GET /search` удалён в версии 3.25 от 22 июня 2026: https://yandex.ru/dev/market/affiliate/ru/concepts/changelog

`/partner/link/create` принимает известный URL товара, списка или корзины и поддерживает `place_id`/`clid`, `vid`, `erid`: https://yandex.ru/dev/market/affiliate/ru/reference/get-partner-link-create

Варианты discovery для spike и последующего включения:

- Yandex Search API web search: https://aistudio.yandex.ru/ru/docs/search-api/quickstart/
- Обратный поиск изображений: https://aistudio.yandex.ru/ru/docs/search-api/operations/search-images-by-pic
- Модель с официальным web-search tool — только если выдаёт проверяемые источники и проходит тот же benchmark.

Основной discovery provider первой реализации — **Yandex Search API**. Механика многошагового поиска от провайдера отделена, чтобы позже добавить другие источники без переписывания run.

## Практический план реализации на Yandex Search API

### 0. Доступ и предохранители

Нужны от владельца:

- `YANDEX_SEARCH_API_KEY` со scope `yc.search-api.execute`;
- `YANDEX_FOLDER_ID`;
- подтверждение активного платёжного аккаунта Yandex Cloud.

Ключ передаётся только через серверный `.env`/секреты окружения. Не записывать его в БД, админку, git, логи, fixtures или результаты benchmark. В админке показывать только `configured: true|false`. Python SDK не добавлять: production backend остаётся на Node 20 и использует REST.

До первого живого вызова задать:

- лимит на benchmark;
- лимит стоимости run и дневной глобальный лимит;
- максимум 8 hero-предметов, 2 раунда и 5 проверяемых кандидатов на раунд;
- синхронные запросы не чаще 1 RPS;
- reverse search выключен по умолчанию;
- функция целиком выключена для пользователей.

Расходы рассчитываются по количеству и типу наших запросов с версионированным тарифом в настройках. Это внутренняя оценка, а не выписка Yandex Cloud. Перед каждым вызовом worker проверяет остаток лимита.

### 1. Живой spike до основной разработки

Сделать отдельный `scripts/procurement-spike.mjs` с ручным запуском и обязательным лимитом запросов. Никаких автоматических вызовов при старте приложения или в unit-тестах.

Проверить на 20–30 заранее размеченных предметах из спальни и гостиной:

- диван/кровать;
- журнальный или обеденный стол;
- ковёр;
- подвесной светильник;
- предмет декора.

Для каждого предмета выполнить только первый точный запрос:

```text
site:market.yandex.ru <категория + форма + материал + цвет + отличительная деталь>
```

Вызов: `POST https://searchapi.api.cloud.yandex.net/v2/web/search`, `FORMAT_XML`, одна страница, ограниченное число групп, регион пользователя/пилота. Декодировать Base64, распарсить XML и сохранить URL, title, snippet и позицию.

На этом этапе проверить:

- доступность ключа и реальную выдачу;
- долю карточек из allowlist среди результатов;
- успешность открытия карточек через importer;
- наличие фото, цены, характеристик и SKU;
- региональные параметры и canonical URL;
- задержку и фактическое число списаний по кабинету;
- качество Top-1/Top-3 после ручной разметки.

После первого раунда на небольшом подмножестве проверить уточняющий второй запрос и reverse search. Reverse вызывать вручную, не более заранее заданного числа раз.

Spike не считается пройденным только потому, что API вернул XML. Нужны реальные проверенные карточки и человеческая оценка сходства.

### 2. Отдельный Yandex provider

Создать `src/yandexsearch.js`:

- `searchWebSync({ query, region, page, limit })`;
- `searchWebDeferred(...)` — следующим этапом;
- `searchByImage({ data|url, site, page })` — отдельный переключатель;
- декодирование Base64 и нормализация результатов;
- таймауты, ограничение размера ответа и маскирование ошибок;
- логирование run/item/round, типа запроса, числа результатов, latency и расчётной стоимости без ключа.

Не делать слепой retry после таймаута: повторный POST может создать второй платёжный запрос. Ошибки 429/5xx обрабатывать ограниченно и только с учётом возможного двойного списания. Deferred operation ID сохранять для возобновления.

Добавить строгий разбор XML через выбранный зависимый parser либо изолированный parser с fixtures; не разбирать произвольный XML ненадёжными регулярными выражениями. Внешние URL и изображения проходят существующую SSRF-защиту.

### 3. Миграция и state machine

Добавить `migrations/023_procurement.sql`:

- `procurement_runs`;
- `procurement_items`;
- `procurement_search_rounds`;
- `procurement_candidates`;
- `procurement_clicks`.

Обязательны уникальные ограничения для идемпотентности run/item/round и дедупликации candidate по canonical URL. В round сохранять query, rejection reasons, provider operation ID, best score, decision, latency и cost.

Создать:

- `src/procurementconfig.js` — defaults + `app_settings.procurement.settings.v1`;
- `src/procurement.js` — orchestrator и переходы состояний;
- `src/procurementjobs.js` — фоновый worker, отдельный от `processRender`;
- запросы в `src/db.js` с owner-check, claim/resume и `FOR UPDATE SKIP LOCKED`.

Run не перезапускает успешные items. После рестарта worker продолжает с последнего незавершённого round. Один run выполняется одним worker; параллельность предметов ограничена настройкой.

### 4. Подробный разбор и crop

В `src/jobs.js`/`src/analysis.js` сохранять существующие краткие `parsed.items` для предварительного фильтра.

Для procurement run добавить один новый Vision-вызов на выбранные 5–8 hero-предметов:

- подробная атрибутная карточка;
- bbox в нормализованных координатах;
- поисковые синонимы;
- confidence и visibility.

Существующим `sharp` создать crop с ограничением координат и размеров, сохранить в `procurement/` storage. Разбор и crop кэшируются и не создаются повторно в каждом раунде.

### 5. Многошаговый worker

Для каждого item:

1. Проверить кэш реальных кандидатов и каталог.
2. Выполнить точный синхронный запрос.
3. Канонизировать URL, оставить страницы из allowlist, удалить дубли.
4. Открыть только до 5 перспективных страниц.
5. Получить реальные данные через безопасную часть `productimport`.
6. Сравнить crop и фото кандидатов.
7. Принять 80+ либо сохранить причины отказа и перейти к уточняющему запросу.
8. После текстовых раундов вызвать reverse только если он разрешён и остался бюджет.
9. Завершить `verified|alternative|unresolved`.

Scorer может оценивать до 5 подписанных изображений кандидатов одним вызовом на раунд и возвращать score breakdown, причины отказа и предлагаемый следующий запрос. Orchestrator, а не модель, применяет hard gates, лимиты и окончательные переходы.

В `productimport.js` отделить безопасное открытие/разбор карточки от добавления в curated `products`. Найденные кандидаты не становятся товарами каталога автоматически. Их изображения и snapshots принадлежат procurement run/кэшу.

### 6. API и UI под feature flag

Backend:

```text
POST  /api/renders/:id/procurement
GET   /api/procurement/:runId
POST  /api/procurement/:runId/items/:itemId/research
PATCH /api/procurement/:runId/items/:itemId/selection
GET   /buy/:candidateId
```

Проверять владельца render/run, feature flag и rate limit. Повторный POST по тому же render с той же конфигурацией возвращает существующий run, а не создаёт новые расходы.

Frontend:

- кнопка «Воплотить дизайн» на выбранной версии;
- отдельный `ProcurementPanel` вместо раздувания `GenerationPanel`;
- прогресс по предметам и частичные результаты;
- карточка: фото, название, цена, магазин, score и его объяснение, `checked_at`;
- основной вариант, альтернативы и unresolved с обычной поисковой ссылкой;
- `/buy/:candidateId` логирует run/item/candidate и делает 302 на canonical URL.

Реферальные ссылки не создаются. Партнёр не влияет на выдачу и score.

### 7. Админка

Новая секция «Поиск товаров»:

- enabled — по умолчанию off;
- Yandex configured — только признак наличия серверного ключа;
- sync search on/off;
- reverse search on/off — по умолчанию off;
- deferred search on/off — до реализации скрыто;
- max items/rounds/candidates;
- min score;
- max run cost и дневной лимит;
- регион и магазин;
- список runs: статус, раунды, стоимость, ошибки, unresolved;
- ручной повтор одного item без повторного поиска остальных.

Сохранение настроек не запускает поиск. Включение feature flag не означает публичный запуск: сначала режим admin-only.

### 8. Отложенные запросы и общий кэш

После стабильного sync-пилота добавить:

- `POST /v2/web/searchAsync`;
- сохранение operation ID;
- polling через Operations API с учётом лимитов;
- обязательное получение результата в течение 12 часов;
- ночной scheduler только в разрешённое окно;
- пакетный добор unresolved и предварительное наполнение кэша типовых предметов.

Отложенный режим не ставить в критический путь интерактивного run: каждый раунд может занять от 5 минут до нескольких часов. Reverse search остаётся синхронным и тарифицируется отдельно.

### 9. Проверки и запуск

Unit/integration без живых платных вызовов:

- XML/Base64 fixtures и нормализация результатов;
- canonical URL и дедупликация;
- построение первого и следующего запроса;
- hard gates, 70/80 и unknown attributes;
- переходы round 1 → 2 → 3 → unresolved;
- ранний выход и запрет лишних вызовов;
- cost limit перед вызовом;
- idempotency и resume после рестарта;
- owner-check и отсутствие секретов в API/логах.

Обязательные команды: `npm test`, `cd web && npm run build`, `npm run docs:llms`, `git diff --check`.

Порядок запуска:

1. Локальный mock integration.
2. Живой spike с ограниченным бюджетом.
3. Локальный canary на реальных рендерах.
4. Деплой с `enabled=false` и добавленными секретами только на VPS.
5. Admin-only canary на 10 рендерах.
6. Проверка ссылок, качества, стоимости и повторного запуска.
7. Только после этого включение ограниченной группе пользователей.

### Definition of done пилота

- Для 5–8 hero-предметов работает многошаговый поиск, а не один запрос.
- Все раунды, причины отказа и расходы видны в админке.
- Основной результат 80+ имеет реальную открытую карточку и проверенные данные.
- 70–79 показаны только как альтернативы; плохие результаты не маскируются ссылками.
- Цель benchmark: не менее 75% предметов получают вариант 80+ в Top-3; иначе публичное включение откладывается.
- Среди выданных прямых ссылок нет заведомо битых или выдуманных.
- Лимиты нельзя превысить повторным нажатием или restart worker.
- Рефералка отключена, поисковые запросы и цены логируются без секретов.
- Тесты и frontend build зелёные, production smoke и admin-only canary пройдены.

## Этапы расширения

1. **Benchmark:** 20–30 размеченных предметов; сравнить провайдеров по Top-1/Top-3, стоимости принятого результата и качеству URL.
2. **Pilot:** одна комната, 5–8 hero-предметов, allowlist магазинов; подробная атрибутная карточка, 2 раунда, проверка карточек, visual score 80, search rounds, feature flag и cost limits.
3. **Расширение покрытия:** 8–12 предметов, отделка, инженерия, текстиль и декор; включать только после приемлемых cost/run и acceptance.
4. **Каталог и кэш:** сохранять удачные кандидаты, обновлять цены, повторно использовать проверенные результаты, разбирать спрос по unresolved items.
5. **Магазины и партнёры:** отдельные официальные адаптеры/фиды, Referral/CPA на outbound, заказы и вознаграждение; без влияния на ранжирование.
6. **Полная закупка:** комплектующие, метраж, регионы, работы, экспорт.

## Метрики

Пилот:

- Top-1/Top-3 human acceptance — главные метрики качества;
- доля предметов с проверенным результатом 80+;
- доля alternative и unresolved;
- распределение успехов по раундам 1/2/3 и причины повторных запросов;
- доля валидных прямых ссылок и свежесть цены;
- стоимость одного принятого товара и полная стоимость run;
- время до первого результата и до завершения run;
- CTR по реальным карточкам и повторное использование приложения.

После расширения:

- покрытие всех видимых предметов;
- качество по категориям и магазинам;
- эффективность кэша и доля повторно использованных карточек;
- заказы и вознаграждение по партнёрам.

Не оптимизироваться только на самооценку модели «80+», количество ссылок или минимальную цену одного API-запроса.
